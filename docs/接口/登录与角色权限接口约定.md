# 登录与角色权限接口约定（供组员 A、B 并行开发）

状态：接口设计已确定，**尚未实现**。适用仓库：`ship-agent-render-release`。组员 A 负责服务端认证、账户和数据归属；组员 B 负责登录界面、角色展示和前端接入。双方以本文件为共同契约，变更接口时先更新本文件并同步对方。

## 1. 现状和目标

当前 `ui/web_server.py` 提供 `GET /`、`GET /healthz`、航次与语音接口，没有登录或角色校验。`/healthz` 公开包含版本、参数和模型模式；`/api/runs/{thread_id}` 与 `/api/resume` 只校验 UUID，没有用户归属。前端 `ui/frontend/app.js` 从 `/healthz` 读取版本和模型状态，并把历史对话、活动任务、方案快照存在浏览器 `localStorage`。

新增两个角色：`user`（普通用户）与 `admin`（管理员）。两者都可使用航次规划。普通用户不接收发布版本、参数档案、服务模型调用状态等管理员诊断字段；管理员可查看这些字段。航次计算依据、软件仿真范围、缺失约束、补能前提等影响判断的信息仍对两种角色显示。前端不得仅靠 CSS 隐藏管理员数据，服务端必须按角色裁剪响应并拒绝越权请求。

## 2. 固定的数据结构

认证方式为服务端会话，浏览器仅保存 `HttpOnly` Cookie，不使用浏览器可读的 Bearer Token。所有时间采用 ISO 8601 UTC，例如 `2026-10-12T04:00:00Z`。

```json
{
  "user": {
    "id": "2d31ad7e-5ee7-4f3c-a1f8-6f328e21d609",
    "username": "operator01",
    "display_name": "值班员",
    "role": "user"
  },
  "csrf_token": "会话绑定的随机令牌",
  "session_expires_at": "2026-10-13T04:00:00Z"
}
```

- `id` 是不可变的用户 UUID；`username` 是登录名；`display_name` 是展示名；`role` 只能是 `user` 或 `admin`。前端可用 `role` 控制布局，但服务端仍独立校验每个请求。
- `csrf_token` 仅用于向同源的写入接口提交 `X-CSRF-Token` 请求头，不放 URL、日志或 `localStorage`。它可以保存在页面内存中，刷新时重新请求 `/api/auth/me`。
- `session_expires_at` 是服务端实际会话过期时间。前端据此做提示，服务端始终负责最终判定。
- 不向浏览器返回密码散列、会话 ID、内部数据库 ID、API 密钥或完整服务配置。

## 3. 认证接口

所有响应均为 `application/json`，同源请求携带 Cookie。登录页、静态资源及健康检查可匿名访问。

| 方法与路径 | 请求 | 成功响应 | 权限 |
|---|---|---|---|
| `POST /api/auth/login` | `{"username":"operator01","password":"..."}` | `200`，返回第 2 节结构并设置会话 Cookie | 匿名；已登录者重新登录时先终止旧会话 |
| `GET /api/auth/me` | 无 | `200`，返回第 2 节结构 | 已登录；用于首屏及刷新恢复 |
| `POST /api/auth/logout` | 请求头 `X-CSRF-Token` | `204`，清除 Cookie 并废止服务端会话 | 已登录；重复登出可返回 `204` |

会话 Cookie 名称固定为 `ship_agent_session`，属性为 `HttpOnly; SameSite=Lax; Path=/`；公网 HTTPS 必须加 `Secure`，本地 `http://127.0.0.1` 可不加。Cookie 值为足够随机的不透明令牌，服务端只存令牌摘要。会话保存在可跨重启共享的持久存储中，不能仅存在进程内存；登出立即失效。初版会话有效期为 24 小时，不自动续期。密码用成熟的慢速密码散列算法保存，不保存明文。账号由部署方建立，初版没有自助注册接口。

`POST /api/auth/login` 校验 JSON 类型和字段长度；账户不存在与密码错误统一返回 `401 invalid_credentials`，避免暴露账户是否存在。登录接口限制连续失败次数；达到限制返回 `429 too_many_attempts`。所有写入请求校验同源 `Origin`，已登录写入请求还须校验会话绑定的 `X-CSRF-Token`。登录成功、刷新恢复、登出、会话失效时，前端据此切换页面，不依赖本地标记假定登录状态。

## 4. 角色和现有接口

| 接口 | 匿名 | `user` | `admin` |
|---|---|---|---|
| `GET /`、`GET /static/*`、`GET /assets/*` | 可访问登录页与公共资源 | 可访问 | 可访问 |
| `GET /healthz` | 仅最小健康字段 | 同匿名 | 同匿名 |
| `GET /api/auth/me`、`POST /api/auth/logout` | `me` 返回 401；登出可 204 | 允许 | 允许 |
| `GET /api/voice/status`、`POST /api/voice/start|chunk|finish` | 401 | 允许，仅操作本人的语音会话 | 允许，仅操作本人的语音会话 |
| `POST /api/run` | 401 | 允许；新任务绑定当前用户 ID | 允许；新任务绑定当前用户 ID |
| `GET /api/runs/{thread_id}`、`POST /api/resume` | 401 | 仅本人任务 | 仅本人任务，默认不跨用户读取 |
| `GET /api/admin/system-status` | 401 | 403 | 200，管理员诊断信息 |

`/healthz` 保留给 Render 健康检查，但响应只含 `{"status":"ok","service":"ship-agent-web"}`（故障时由现有健康机制返回非成功状态）。原有 `release`、`llm_mode`、`checkpoint_backend`、`checkpoint_ready`、`speech_mode`、参数容量与 SOC 下限等信息迁移到 `GET /api/admin/system-status`，不可继续留在匿名接口、HTML 初始内容或公开静态配置中。管理员接口成功响应结构：

```json
{
  "status": "ok",
  "release": {
    "baseline_id": "ship-agent-render-release",
    "app_version": "1.0.0",
    "parameter_profile": "synthetic_demo_user_override_2026-09-23",
    "parameter_approved_at": "2026-09-23"
  },
  "llm_mode": "enabled",
  "checkpoint_backend": "postgres",
  "checkpoint_ready": true,
  "speech_mode": "iflytek_iat"
}
```

`release` 可以包含当前 `/healthz` 的其他非密钥诊断字段；不得包含密码、数据库连接串或模型 API 密钥。`llm_mode=enabled` 只表示服务已配置，不表示某个任务实际调用成功。管理员查看单次调用结果时，以该任务真实的模型调用记录为准。

任务归属必须持久化并由服务端校验：创建任务时将 `thread_id` 与用户 ID 原子关联；读取或恢复之前先查归属，不能把 UUID 当访问凭据。对于他人任务和不存在的任务统一返回 `404 workflow_not_found`，避免泄露任务存在性。部署前产生、没有归属记录的旧 `thread_id` 默认不允许任何普通用户恢复；如需迁移，由组员 A 单独制定管理员可审计的迁移方案。管理员默认也只访问自己的航次，不自动拥有读取所有用户航次的权限。

现有语音 `session_id` 同样绑定创建者，会话结束或过期时失效；不能凭 `session_id` 操作其他用户的录音。前端当前浏览器的历史记录和只读快照按用户 ID 隔离。切换账号或登出时清除当前展示和浏览器中的敏感快照；管理员诊断数据不得写入普通用户可复用的缓存。服务端任务归属是最终依据，浏览器快照不能绕过服务器授权或恢复旧的待确认操作。

## 5. 普通用户与管理员的响应边界

普通用户界面不显示版本号、参数档案编号/日期、模型配置与调用状态、模型故障排查文案。管理员界面可显示这些信息。`GET /api/admin/system-status` 仅管理员可调用；普通用户页面不请求它。

航次接口 `POST /api/run`、`POST /api/resume`、`GET /api/runs/{thread_id}` 的普通用户响应保留现有 `status`、`thread_id`、`request`、`report`、`plan`、`adjustment_options`、必要的工具结论与风险提示，以维持规划流程；服务端另设角色化序列化/过滤层，移除仅供排障的模型调用模式、原始内部异常和敏感诊断数据。管理员可取得完整的非敏感诊断字段。组员 A 应列出最终过滤字段清单，组员 B 不得依赖普通用户响应中出现管理员字段。

科学模型名称、参数来源、适用范围、软件仿真性质以及真实限速/船闸等待/补能条件的未知项属于结果依据，不能因隐藏 AI 状态而删除。普通用户界面不宣称“已调用 AI”或“AI 生成”，除非该任务确有调用记录且产品决定明确显示；模型未调用时仍能如实呈现五工具计算结果。`final_message`、`task_understanding`、`dashboard` 等现有字符串可能含“模型/AI/版本”字样，组员 A 和 B 应共同检查，不得仅过滤顶层字段。

## 6. 错误格式和前端处理

新认证与权限错误统一使用现有项目风格：

```json
{"status":"failed","error":"auth_required","message":"请登录后继续"}
```

| HTTP | `error` | 使用场景 | 前端处理 |
|---|---|---|---|
| 400 | `invalid_auth_request` | 登录 JSON 或字段无效 | 提示检查输入 |
| 401 | `invalid_credentials` | 账号或密码错误 | 在登录框提示，不区分账号与密码 |
| 401 | `auth_required` | 未登录或会话失效 | 清理当前展示，回到登录页；登录后可重新读取本人服务器任务 |
| 403 | `forbidden` | 角色不足、CSRF/来源校验失败 | 显示无权限或请求失效；不要重试写入 |
| 404 | `workflow_not_found` | 任务不存在或不属于当前用户 | 移除失效的本地活动任务引用 |
| 429 | `too_many_attempts` | 登录尝试过多 | 显示稍后再试 |
| 503 | `auth_unavailable` | 认证存储暂不可用 | 显示服务暂不可用，不进入工作台 |

`message` 为简短中文，可供界面直接显示；`error` 为稳定机器码。现有航次业务错误码继续沿用，不把所有业务错误改成认证错误。前端对每个受保护 `fetch` 统一处理 `401 auth_required`，不要仅在登录时处理；管理员接口的 `403` 切回适当页面。所有响应继续设置 `Cache-Control: no-store`。

## 7. 双方开发边界与交接

- **组员 A**：负责 `ui/web_server.py`、认证/用户持久层、任务和语音归属、角色化响应、部署所需密钥配置；提供两个非真实账号的本地测试方法。不得提交真实密码或密钥。
- **组员 B**：负责 `ui/frontend/index.html`、`app.js`、样式及登录交互。先调用 `/api/auth/me` 决定显示登录页或工作台；登录/登出使用上述接口；所有写入请求加 `X-CSRF-Token`，请求保持同源 Cookie。普通用户不调用管理员接口。
- 如两人均需编辑某文件，先由该文件负责人落地，再以单独提交交接；不要同时改同一文件。新增接口字段或错误码须先更新此文档。

联调至少覆盖：匿名访问受保护接口；两种角色登录与刷新；普通用户直连管理员接口；用户 A 访问/恢复用户 B 的任务和语音会话；退出后旧 Cookie 失效；切换账号后浏览器历史隔离；公网 `/healthz` 不泄露诊断信息；普通用户与管理员各自看到的状态和结果文案。当前文档是实现约定，并不表示这些行为已上线。

## 8. 提交给负责人审核

两位组员分别在自己的本地仓库从最新 `main` 建立分支，组员 A 使用 `feat/auth-backend`，组员 B 使用 `feat/auth-frontend`。不要直接向 `main` 推送各自的实现，也不要自行合并 Pull Request。

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/auth-backend   # 组员 B 改为 feat/auth-frontend
# 完成修改后，先用 git status 检查待提交文件，再只暂存自己负责的文件
git status --short
git add -- ui/web_server.py        # 示例；新增文件和其他已修改文件逐个追加
git diff --cached --stat
git commit -m "Add authentication and role enforcement"
git push -u origin feat/auth-backend
```

组员 B 将示例中的分支名和提交说明分别改为 `feat/auth-frontend`、`Add login and role-based UI`。若 GitHub 不允许直接推送到项目分支，可在自己的 fork 建同名分支，并向原仓库 `main` 发起 Pull Request。

推送后在 GitHub 创建以项目 `main` 为目标的 Pull Request，描述实现范围、接口差异、配置项、验证步骤和结果；附普通用户与管理员各一张界面截图。把 PR 链接发给负责人审核。发现接口约定需要变更时，先在 PR 描述中说明并更新本文件，等另一位组员同步后再继续接入。若另一人的 PR 先合并，后合并者先同步最新 `main` 并解决冲突，再更新自己的 PR。
