## 2. 文件与基本调用

| 文件 | 用途 |
|---|---|
| schemas/types.py | 请求、船态、航段、计算结果、方案及工具信封 |
| schemas/validate.py | 严格解码、缺参识别、范围和一致性校验 |
| configs/examples/voyage_request.json | 非敏感请求示例 |
| tests/test_schemas.py | 契约与异常测试 |

```python
import json
from pathlib import Path

from schemas.types import Status, VoyageRequest
from schemas.validate import parse_request, require_valid

payload = json.loads(
    Path("configs/examples/voyage_request.json").read_text(encoding="utf-8")
)
request, validation = parse_request(payload)

if validation.status == Status.NEED_CLARIFICATION:
    print(validation.missing_fields)
    print(validation.questions)
elif not validation.valid:
    print(validation.issues)
else:
    require_valid(request)
    print(request.to_dict())
```

每个业务结构提供：

- `to_dict()`：转换为 JSON 可用字典，保留未知值为 null。
- `from_dict()`：严格检查字段类型并恢复嵌套结构，不检查业务是否可执行。
- `validate(record)`：检查业务缺项、范围与一致性，返回结果，不修改输入。
- `require_valid(record)`：未通过校验时抛出 SchemaValidationError。

未知字段、布尔值冒充数值、数值字符串、NaN/Infinity 均不静默接收。JSON 的整数可用于浮点字段，解码后归一为 float。

注意：`validate(...).valid` 表示该记录通过校验，不表示任务可行。不可行结果也可以是一份正确的记录；还须检查工具 status、OptimizationResult.feasible、ManagementPlan.safe 和最终 VoyagePlan.status。

## 3. 单位、空值与来源

| 量 | 内部单位/格式 |
|---|---|
| 距离 | km |
| 速度 | km/h；节需显式乘 1.852 |
| 时间长度 | h，含等待时统一为小时 |
| 功率 | kW |
| 能量 | kWh |
| SOC | 0–1 |
| 吃水 | m |
| 时间点 | 带时区 ISO 8601，例如 2026-09-18T09:00:00+08:00 |

null 表示未知。明确核实等待时间为零时才填 0；未知时不填 0。容量、安全阈值、限速、功率、充电能力由 B/C 提供来源，并由 A 确认采用值。代码没有填入真实船舶默认安全阈值。

SourceRef：

- source_id：来源文件、用户输入、测量记录、模型/工具或演示假设标识。
- kind：document / user / measurement / assumption / tool。
- locator：页码、表格、字段、记录位置，可为空。
- confirmed：来源是否完成核实，不由解码自动设为 true。
- note：解释和使用边界。

ParameterValue 保存 value、unit、source。DataConflict 保存字段名、候选值和 resolution。未处理冲突不可直接作为完整取数结果继续计算。

校验能够检查来源记录是否存在，不能代替人工核实真实性。演示假设应标为 assumption、写入 assumptions；不能冒充核实事实。

## 4. 状态与失败处理

| status | 意义 | 调用方动作 |
|---|---|---|
| ok | 当前工具执行成功/完整方案通过校验 | 继续调用；最终报告仍须验证完整 VoyagePlan |
| need_clarification | 缺少关键参数或有未解决冲突 | 显示 missing_fields 与 questions，等待补充 |
| invalid_input | 类型、范围、字段或一致性非法 | 说明问题，拒绝继续计算 |
| infeasible | 输入可用，但不存在满足条件的方案 | 给出分类与原因，后续工具试算调整方向 |
| failed | 工具或服务执行失败 | 显示 reason，不伪装成功 |
| awaiting_choice | 编排等待用户选择调整方向 | 预留状态，人工选择流程另行实现 |

infeasible_type：time / soc / power / route / combined。

ToolResponse 字段：tool、status、payload、missing_fields、questions、reason、infeasible_type。

- ok：必须有符合对应工具结构的 payload，不能同时带缺参追问或不可行分类；五工具的 payload 会自动进行业务校验，空字典/空结果列表不视为成功。
- need_clarification：必须有 missing_fields 和 questions；可保留部分诊断数据。
- infeasible：必须有 reason 与 infeasible_type。
- failed / invalid_input：必须有 reason。
- payload 是 JSON 字典。工具名固定为 Tdata / Tseg / Tenergy / Tspeed / Tmanagement；工具实现先验证记录，再放入信封调用 validate(response)，校验会按工具名解码并检查成功结果。
- awaiting_choice 仅用于 VoyagePlan 的编排状态，不作为五个计算工具的返回状态。

非 ok 的 VoyagePlan 可以保留部分请求和诊断结果，不要求存在完整计算方案。所有嵌套字段仍检查类型；need_clarification 必须给出 clarification_questions，其他非 ok 状态必须给出 reason。完整数值与安全校验仅在最终 status=ok 时执行，诊断结果不可用于展示成功计划。

## 5. 请求与事实配置

### VoyageRequest

| 字段 | 说明 |
|---|---|
| origin / destination | 起终点；缺失追问，归一化由解析器/Tdata 完成 |
| departure_at | 出发时间；有绝对到达截止时间时必需 |
| arrival_deadline | 绝对到达截止时间，可为空 |
| max_duration_h | 最长总耗时，可为空；与 arrival_deadline 至少给一个 |
| soc_initial | 初始 SOC，缺失追问 |
| load_state / draft_m | 载况/吃水，至少提供一个；转换与补充须有依据 |
| environment | 环境参数及来源，没有值时保持空字典 |

同时提供两种时间约束时，方案需同时满足。仅提供相对最长耗时、没有出发时间时，可以保留任务用于耗时规划，但不能生成 ETA。提供出发时间后，成功方案需输出一致的 ETA。

示例 JSON 是人为填写的请求，不是航行测量或可行性证明。其中路线、SOC、载况和时限不意味着已经通过船舶参数、路线限制或能量预算校验。

### VesselState

字段：vessel_id、capacity_kwh、soc_initial、soc_min、soc_alarm、max_power_kw、auxiliary_power_kw、draft_m、sources、assumptions。

计算准备状态需 capacity_kwh、soc_initial、soc_min、max_power_kw、auxiliary_power_kw 均已采用并记录来源。soc_alarm 可以保持未知；不能将停机阈值自动当作规划安全下限。

sources 的键与参数名一致，例如 sources["capacity_kwh"]。显式的辅助功率 0 也必须有依据或已批准假设。

功率上限、模型平均/峰值功率必须采用相同计量边界与条件。B 要确认额定/最大/运行功率及电池侧、输入侧等差异，不能直接混用；需要换算时记录方法并交 A 确认。来源、转换与采用参数决定保留在配置说明中，本次不填入未经确认的真实值。

### DataContext

字段：vessel、route_id、parameters、conflicts、missing_fields、assumptions。

记录本次采用值及来源。未采用的候选事实可保留在配置/冲突清单中；不要把无关、尚未采用的值混入 parameters 导致计算使用。

## 6. 五工具职责与交换结构

以下为待实现函数的契约，函数名用于统一协作；此次尚未创建真实工具实现。

| 工具 | 负责人 | 输入 | ToolResponse.payload |
|---|---|---|---|
| Tdata | C | VoyageRequest + 船舶/航线事实配置 | DataContext.to_dict() |
| Tseg | C | VoyageRequest + DataContext + 航线配置 | {"segments": [Segment.to_dict(), ...]} |
| Tenergy | B | 航段、DataContext、候选航速 | {"candidate_results": [EnergyResult.to_dict(), ...]} |
| Tspeed | B | 请求、航段、候选能耗结果、采用约束 | OptimizationResult.to_dict() |
| Tmanagement | B | 请求、DataContext、选定方案 | ManagementPlan.to_dict() |

- Tenergy 可以对同一航段产生多个候选速度；OptimizationResult.energy_results 每段只保留一个选定结果。
- Tspeed 的阶段可行性不是最终能量安全结论。Tmanagement 未通过时，编排必须回传不可行/追问并重算，不能输出最终成功方案。
- 每个工具返回前验证自己的 payload；编排收到后再次检查，错误停止。
- 缺项必须定位到字段；执行异常转换为 failed，而不是返回空的成功数据。

### Segment

字段：segment_id、origin、destination、distance_km、max_speed_kmh、min_speed_kmh、waiting_h、source、assumptions。

执行计算需要正距离、已知限速、已知等待时间及来源。min_speed_kmh 可为空，表示未声明最低限制；候选航速仍需满足数值模型适用范围。

子航线和反向航线由 Tseg 按实际顺序返回。不改变 segment_id 所代表的事实含义；最终结果与输入列表顺序一致。

### EnergyResult

字段：segment_id、speed_kmh、power_kw、duration_h、energy_kwh、energy_scope、model_id、peak_power_kw、assumptions。

- duration_h 是该段总耗时，包含 waiting_h。
- power_kw 是与 energy_kwh 相同计量边界、相同总时间范围的平均功率。
- energy_kwh = power_kw × duration_h；等待消耗不能漏算或重复加入。
- energy_scope 必填：propulsion（推进能耗）或 total（总能耗）。B/A 必须确认模型数据口径后明确设置，不依赖默认值。
- peak_power_kw 用于功率限制检查，最终成功方案必须有依据；不将平均功率自动当峰值。
- power_kw、peak_power_kw 与 max_power_kw 必须处于可比较的同一功率边界；模型输出能量采用对应的电池侧消耗口径。推进轴功率等原始量需由 B 显式转换，不能直接当电池能耗。
- 本结构是候选航行消耗预测，不是原始瞬时功率记录；原始负功率数据由 B 检查回馈等含义，不直接依据本结构规则删除。
- model_id 记录数值模型/方法标识，适用范围和假设写明。

### OptimizationResult

字段：feasible、energy_scope、energy_results、total_energy_kwh、total_duration_h、eta、infeasible_type、reason、checks、search_description、assumptions。

可行结果需有分段结果与汇总；分段能耗口径一致。checks 至少包含 time、speed、power，passed 为明确 true。None 表示约束尚未核实。

不可行结果需分类和原因，选定 energy_results 为空、汇总/ETA 为 null。调整选项的试算作为另一次独立结果保存，不能混成已选定方案。

search_description 写明算法、候选范围与粒度；不据此声称连续全局最优。

### ManagementPlan

字段：safe、soc_initial、soc_final、soc_min、capacity_kwh、available_energy_kwh、required_energy_kwh、auxiliary_energy_kwh、charge_required_kwh、soc_trajectory、checks、warnings、assumptions。

- safe=True 需要完整预算、已知辅助能耗、已知补能需求、分段 SOC 及已通过的 soc 约束。
- SOC 初始/末端/分段均在 0–1，安全方案不越过采用下限。
- soc_final 与最后一个 SocPoint 一致；SocPoint 是分段结束时的 SOC。
- required_energy_kwh 是总能量需求。
- 优化结果为 propulsion 时，总需求 = 优化推进能耗 + 辅助能耗，辅助能耗不能未知。
- 优化结果为 total 时，直接使用总能耗，不重复加辅助能耗。
- charge_required_kwh 为 null 表示尚未确定，不能解释为无需充电；若 >0，不能将尚未补能的任务直接标为安全。
- 当前航行方案使用同一个采用有效容量，能耗以电池侧消耗计；安全预算不超过 capacity_kwh × max(soc_initial - soc_min, 0)，允许另扣有依据的安全余量。
- 未执行途中补能的成功方案需满足：required_energy_kwh = capacity_kwh × (soc_initial - soc_final)，分段 SOC 不凭空增加。相关损耗由 B 计入电池侧消耗并说明，不重复计入容量或辅助能耗。
- total 口径下，每段 SOC 下降对应的电量需等于该段总能耗；propulsion 口径下至少覆盖该段推进能耗，辅助能耗分配由 B 记录并实现。辅助能耗不能大于总能耗。
- 真实容量、损耗参数、功率换算与辅助负载处理由 B 实现并提供依据，采用值由 A 决定；上述关系是接口一致性约定，没有替团队选定实船参数。

## 7. 最终方案与编排约定

VoyagePlan 字段：request、status、data、segments、optimization、management、clarification_questions、reason、assumptions、trace。

完整成功方案必须：

1. 请求和数据准备通过校验。
2. 航段连续，起终点匹配请求，顺序匹配选定结果和 SOC 轨迹。
3. 航速满足航段限速；总耗时与距离、速度及等待时间一致。
4. 总耗时满足用户约束；ETA 有真实出发时间且与耗时一致。
5. 峰值功率不超过采用上限，能量管理明确安全。
6. 请求、船态、能量管理的 SOC、容量与安全下限一致。
7. 汇总与分段结果一致；总能量需求的推进/辅助口径明确。

当前校验检查输入输出一致性；具体数值模型、分段 SOC 演化、适用范围、搜索覆盖和参数换算仍由 B 实现并验证，不能将接口测试当作实船效果证明。

TraceEvent 保存 tool、status、message、input_id。编排还应保存输入/配置快照或其关联 ID，使报告数字能够追溯到本次工具输出。

用户修改起终点/环境/载况后重新取数并计算；改变时间/SOC 后重新校验受影响约束与结果。最多两轮重算，人工选择及结果失效机制由 A 后续实现，此次没有伪装成已完成能力。

报告必须从通过校验的工具字段取数字，大模型仅负责解释。报告字段一致性校验另行实现，不在本次 A2 的代码范围内。
