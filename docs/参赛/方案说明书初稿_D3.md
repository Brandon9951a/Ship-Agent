# 绿航智算——大语言模型驱动的船舶航速优化与能量管理智能体

方案说明书初稿（D3，2026-09-20）。本文按赛事八章结构整理当前可核验成果。所有“已实现”均以当前 A 集成分支代码和自动测试为依据；所有“仿真验证”均限定为 `synthetic_demo` 软件演示，不代表实船安全、运营批准、法定航道限速或真实模型标定。

## 第1章 项目概述

### 1.1 背景与定位

纯电动内河船舶的航行决策需要同时考虑航线、到达时间、航速、推进与辅助能耗、电池荷电状态和安全边界。上述信息来自不同资料或系统，且部分运营参数可能缺失。绿航智算面向豫交投001和平顶山港—周口港航线，定位为船员与调度人员的航行辅助决策原型，不替代船员判断、BMS保护、航道管理要求或运营审批。

### 1.2 项目目标

系统接收自然语言或结构化航行任务，依次完成数据准备、航段划分、候选能耗计算、航速搜索和能量管理，输出航段、速度、ETA、能耗、SOC轨迹、约束检查、告警、单位和来源。关键参数缺失或任务不可行时停止计算并说明原因，不用大语言模型猜测工程数值。

### 1.3 当前创新点及状态

| 创新点 | 实现方式 | 当前状态 |
|---|---|---|
| 自然语言与工程计算解耦 | 确定性解析和Schema锁定参数，大模型只做不含工程数值的语义确认与解释 | 已实现 |
| 五工具可审计链路 | `Tdata → Tseg → Tenergy → Tspeed → Tmanagement`逐步传递结构化结果并校验 | 已实现 |
| 安全优先的拒绝机制 | 缺参、非法输入、时间/SOC/功率不可行或工具失败时立即停止 | 已实现基础能力 |
| 单位和来源随结果输出 | 航段距离、功率上限、容量、SOC阈值和模型编号随报告保存 | 已实现 |
| 用户调整后重算 | 用户选择调整时间或能量条件后恢复流程 | 后续规划 |

## 第2章 需求分析

### 2.1 场景问题

任务通常由起终点、出发或到达约束、初始SOC、载况或吃水组成。航线资料能提供港闸顺序和距离，但逐段法定或运营限速、船闸内部通行时间、充电设施能力等信息可能不完整。系统必须区分“资料事实”“演示假设”和“工具计算结果”，避免将缺失信息补成看似完整的方案。

### 2.2 用户需求与依据

当前需求来自船舶调研资料、历史航行数据、港闸距离材料和团队场景分析，尚未开展可对外声明的真实用户访谈或满意度调查。历史数据只用于检查演示速度覆盖，不能在通道含义、单位、功率计量边界和时间重复机制未确认时宣称完成能耗模型标定。

| 场景 | 系统行为 | D3状态 | 证据方式 |
|---|---|---|---|
| 正常可行 | 输出航段、速度、ETA、能耗、SOC、检查和来源 | 已完成软件演示 | 端到端脚本与自动测试 |
| 缺少参数 | 返回缺失字段和追问，不调用后续工具 | 已实现 | 缺参测试 |
| 时间不可行 | 返回时间不可行并停止，不强行提高速度 | 已实现基础用例 | 紧时限测试 |
| SOC或功率不可行 | 返回约束检查、告警或能量缺口 | 已实现计算基础 | 单元测试；系统场景待补 |
| 服务故障 | 工具失败即停；大模型失败则仅对文本说明模板回退 | 已实现 | 故障和回退测试 |
| 多轮用户调整 | 保留用户选择并只重算受影响节点 | 未实现 | 后续多轮用例 |

### 2.3 安全需求

软件关注线、规划安全下限、警告线和临界线分别配置为35%、30%、25%和20%。20%以下由操作员和BMS处理；系统不得发送断电、接触器或推进控制命令。硬件断电阈值未知，不能由软件推定。双电池规则用于生成角色建议：组1推进优先，组2日常负载优先并可在必要时辅助推进；缺少分组初始SOC和真实拓扑时只计算汇总SOC。

## 第3章 解决方案设计

### 3.1 总体架构

用户输入先经过确定性解析和Schema校验，再进入LangGraph状态机。Tdata加载船舶、航线、限制和演示策略；Tseg生成连续航段；Tenergy对候选速度计算推进能耗；Tspeed执行离散搜索并检查时间、速度、功率和SOC；Tmanagement生成汇总SOC轨迹、告警、补能缺口和双电池角色建议；最终报告汇总单位、来源、模型编号和适用边界。

### 3.2 大语言模型边界

DeepSeek官方API的非思考模式仅用于任务理解边界确认和结果的定性解释。结构化请求仍由确定性解析器产生，工程数值只能来自配置或计算工具。模型输出含阿拉伯数字、中文数字、工程单位或SOC等工程表达时，系统拒绝该文本并使用模板；API失败、超时或不可用同样回退，不影响五工具的确定性计算。

### 3.3 演示模型与搜索方法

由于真实三次方模型尚未标定，D3将模型单独配置为 `synthetic_demo_survey_anchor_v1`。调研资料给出经济工况约6 kn、推进功率约90 kW，据此得到演示系数：

\[
a=90/(11.112)^3=0.06559425611908812\ \mathrm{kW/(km/h)^3}
\]

推进功率按 \(P=a v^3\) 计算，辅助负载按30 kW单独累计。候选速度为7.408、9.26和11.112 km/h；11.112 km/h只是在指定演示路线上的软件运行上限，不是航道法定限速。Tspeed在候选组合中选择满足到达约束、逐段上限、200 kW运行功率上限和SOC规划下限的低能耗方案。

### 3.4 电池与能量口径

总标称容量为1567.85 kWh，两组各783.925 kWh，不重复相加。软件演示初始SOH为90%，因此能量预算使用1411.065 kWh有效总容量。250 kW仅保留为额定候选，D3功率可行性使用约200 kW最大运行功率。能量管理只给出建议和风险说明，不执行硬件控制。

## 第4章 项目实施

### 4.1 已实现模块

- 完成统一Schema、字段单位、来源对象、状态和交叉一致性校验。
- 完成中文任务解析、缺参追问和结构化任务入口。
- 将LangGraph默认流程接入五个真实工具适配器，并实现失败即停。
- 接入离散航速搜索、汇总SOC轨迹、阈值告警、补能缺口和双电池角色建议。
- 完成带单位与来源的报告、受控模型文本和模板回退。
- 文本UI已消费真实五工具、计划和报告结构；图形化表格和曲线仍待完善。

### 4.2 数据处理现状

项目持有一份XLSX和两份CSV历史航行数据。首轮检查发现时间重复、多快照、负值符号、单位和测量边界仍有待确认项。D3未使用这些数据拟合正式能耗系数，只核对历史正值样本的速度覆盖可达到演示经济航速附近。环境回放后续应使用连续历史时间片段，并记录来源、时间范围和随机种子，统一表述为“历史数据驱动模拟”。

### 4.3 团队分工与协作

A负责架构、LangGraph、模型调用边界、决策审核、报告和统稿；B负责能耗、航速优化、SOC/能量管理与数值验证；C负责航线数据、Tdata/Tseg、界面、场景需求和展示材料。成员在个人分支提交，由A复核测试后合并；参数、接口和安全范围变化由A确认。

## 第5章 测试与验证

### 5.1 验证方法

当前验证由Schema与单元测试、工具级测试、LangGraph停止路由测试、模型失败回退测试和正常任务端到端脚本组成。验收命令包括全量Pytest、`pip check`、`git diff --check`和独立D3演示脚本。测试证明软件行为与接口一致，不证明实船节能、安全或运营可用性。

### 5.2 正常任务仿真结果

任务为2026-09-21 08:00从平顶山港出发，要求11:00前到达军李船闸，初始SOC 85%，半载。工具链输出如下：

| 指标 | 结果 | 单位/来源 |
|---|---:|---|
| 航段距离 | 25.5 | km；港闸距离资料 |
| 选择速度 | 9.26 | km/h；演示候选集合 |
| 航行时间 | 2.75377969762419 | h；距离/速度计算 |
| ETA | 2026-09-21T10:45:13.606911+08:00 | ISO 8601；工具计算 |
| 推进能耗 | 143.42602591792655 | kWh；演示三次方模型 |
| 辅助能耗 | 82.6133909287257 | kWh；30 kW演示负载 |
| 总需求能量 | 226.03941684665227 | kWh；工具汇总 |
| 初始/结束SOC | 0.85 / 0.6898093519103285 | fraction；工具计算 |
| 峰值推进功率 | 52.08333333333333 | kW；演示模型 |
| 补能缺口 | 0 | kWh；软件能量预算 |

该任务选择在首段子航线上验证，避免把未知的船闸内部通行距离或时间补入正常结果。当前分支全量自动测试记录为373项通过，依赖检查无损坏，空白检查通过；最终提交前须在冻结提交上再次复测并更新数量。

### 5.3 尚未完成的验证

仍需补充低SOC系统场景、多轮调整、反向完整航线、船闸实际通行、充电可用性、性能统计、模型标定验证、独立误差评估和实船试验。没有同约束、同口径的可靠基准前，不报告节能率。

## 第6章 应用效果与成果

D3形成了一条可复现的正常任务软件演示主线：从自然语言输入到五工具计算，再到带来源和边界的结构化报告。当前可验证效果是减少手工串联计算、对缺参和不可行任务显式停止、保留数值来源，以及在模型服务异常时维持确定性工具输出。

上述成果属于原型和离线仿真验证。项目尚无可对外声明的实船部署、真实运营节能比例、法定航行批准、真实用户满意度或充电成功验证。推广应用前需要确认真实限速、船闸过程、充电设施、电池拓扑、BMS接口、数据权限及操作规程，并开展独立数值验证和实船安全评审。

## 第7章 总结与展望

D3已打通正常子航线的五工具端到端链路，建立了“工程数值由工具负责、大模型只做受控文本”的责任边界，并用显式 `synthetic_demo` 配置隔离演示参数。系统能够输出航段、速度、ETA、能耗、SOC、风险说明、单位和来源，也能在缺参、工具失败或部分约束不可行时停止。

主要局限是逐段限速、船闸通行、充电能力和真实能耗标定尚未关闭；历史数据字段语义和采集机制仍需核实；目前只有汇总SOC而非分组动态；UI仍以结构化文本输出为主。后续优先完成真实数据字典和功率口径确认、时间分组的模型标定与独立验证、三类系统场景、多轮调整恢复、图形化UI和实船前安全审查。
