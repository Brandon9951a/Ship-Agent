## 一、第一天的目标与范围

第一天结束时，团队必须获得一套可以据此并行开发的基线：

1. 三个人都能从共享仓库安装工程、运行入口和现有测试。
2. A 给出统一的数据结构、工具接口、失败状态和最小数据样例。
3. B 给出船舶参数来源、冲突清单、首轮数据检查及能耗计算口径。
4. C 给出完整航线事实、数据获取规则、演示场景与说明书提纲素材。
5. A/B/C 共同确认：哪些数据已核实，哪些仅用于演示假设，哪些仍缺失。
6. 第一批任务通过 PR 合入，所有交付物有文件路径、负责人和验收记录。

当天不要求完成 LangGraph 全流程、真实航速优化、完整 UI、成稿说明书或视频。不要把占位代码可运行写成已具备真实规划能力。

本周聚焦文字交互、五工具链、可行性判断、用户选择后重算和可信报告。暂不安排语音、完整多船系统、复杂电池功率分配、模型训练或本地大模型部署。

### A2. 定义统一数据结构与工具契约（P0，中午前给草案）

负责文件：

- `schemas/types.py`：业务结构。
- `schemas/validate.py`：最小校验。
- `docs/接口/五工具接口契约.md`：字段、单位、空值、错误与工具职责。
- `tests/test_schemas.py`：结构与校验测试。
- `configs/examples/voyage_request.json`：不包含敏感信息的任务样例。

以上为待创建的交付路径。保留现有消息结构和入口兼容性，不能为了换接口把现有测试直接破坏。

建议最小契约如下，经 A/B/C 评审后确定：

| 结构 | 必须说明的内容 |
|---|---|
| VoyageRequest | 起点、终点、出发时间、到达约束、初始 SOC、载况/吃水、环境输入与缺失项 |
| DataContext | 已采用参数、来源、优先级、冲突、假设、待澄清字段 |
| Segment | 航段 ID、起终点、距离、限速、等待时间、适用方向及来源 |
| EnergyResult | 航段、候选航速、功率、耗时、能耗、计算方法与适用范围 |
| OptimizationResult | 可行性、采用航速、耗时/ETA、总能耗、约束检查、不可行原因 |
| ManagementPlan | 初始/末端 SOC、分段 SOC、能量预算、告警、补能需求与未知项 |
| VoyagePlan | 任务、参数快照、工具结果、状态、解释、假设、追踪信息 |

必须明确：

- 速度统一 km/h，距离 km，时间 h，功率 kW，能量 kWh。
- 推荐内部 SOC 使用 0–1，界面显示百分比；当天明确并固定，不混用。
- 时间采用带时区的格式；ETA 缺出发时间时不得自行补造。
- 未知限速、等待时间和充电功率不能默认填 0。
- 缺参数、输入非法、不可行和执行失败要区分，不能都返回“成功”。
- 工具负责工程数值；报告只引用已验证的工具字段。
- `Tdata → Tseg → Tenergy → Tspeed → Tmanagement` 的具体入参、出参、错误行为由契约记录；最终报告以完整约束校验为准。
- 航速搜索的可行性与 SOC 校验失败应有明确回传路径，不允许输出未通过能量校验的方案。
- 用户补充信息、调整目标和重算时，哪些输入变化、哪些结果失效，应写入契约。
- 增加字段须通知依赖方；接口确认后避免无通知改名。

验收：

- 有一个合法样例能通过校验。
- 非法 SOC、负距离、缺少必要信息有测试或明确状态。
- 缺失项被保留，不通过虚构默认值“填齐”。
- B/C 确认接口足以开展各自模块；现有基础测试仍通过。

## 五、B：计算与验证负责人任务

### B1. 船舶事实、采用值与安全边界（P0）

先读：成员阅读清单、本周接口要求、船舶参数文件、资料包中的船舶调研报告。

交付：

- `configs/vessel_facts.yaml`。
- `configs/limits.yaml`。
- `docs/数据/船舶参数与冲突清单.md`。

每个关键参数至少记录：名称、单位、候选值、来源文件与页码/位置、使用场景、拟采用值、确认状态、确认人。允许采用值为空，不允许用猜测掩盖缺口。

重点核查：

- 电池可用容量与总容量是否一致；约 1567 kWh 的口径。
- 两组约 783.93 kWh 电池的用途与连接方式，不能重复累计或擅自假设可任意切换。
- 设计与调研中的电机功率不同，分别注明额定、最大、运行值。
- 13 km/h、约 6 节等速度的场景和单位；1 节 = 1.852 km/h。
- 设计吃水与调研空载/满载吃水差异。
- 25% 告警、20% 停机的来源与含义；规划安全下限须另外确认，不能自动等同停机阈值。
- 生活负载和推进负载是否纳入当前能耗预算。
- 已知充电地点、充电时长；没有依据时不写数值充电功率或沿途可补能承诺。

验收：关键参数有来源；冲突显式列出；A 确认本周演示采用的参数集。尚未核实的演示假设须单独标注，不能宣称适用于真实船舶运行。

### B2. 首轮数据体检和字段字典（P0）

输入：资料包中的 `data.xlsx` 与两份航行 CSV。原始数据保持只读，不直接覆盖。

交付：

- `scripts/inspect_data.py`：可复跑的读取与检查脚本。
- `docs/数据/字段字典.md`。
- `docs/数据/D1_数据检查报告.md`。
- 如需示例，提交经权限核实的小型脱敏样例；不提交整份原始数据。

检查内容：

1. 文件、工作表、行列数、编码、时间范围和字段类型。
2. 时间戳顺序、重复、缺失、采样间隔与大段中断。
3. 航速、功率、电压、电流、SOC、位置、载况等关键字段的单位与含义。
4. 无名列及 Excel 中类似 `Unnamed:3` 的异常列。
5. 负功率/负电流可能表示回馈或测量口径差异，不直接全删。
6. 多电池通道、累计电量与瞬时功率是否被重复统计。
7. 是否能够关联航段、载况与航次；无法关联时说明限制。

字段字典当天至少覆盖计算必需字段；其他字段列为待确认，不能声称全部解释完成。

验收：脚本能在本地指定数据路径运行；报告有实际检查结果、单位疑点与清洗建议。原始数据体检不是训练结果，不能用来填性能指标。

### B3. 明确计算基线与验证设计（P0）

交付：`docs/算法/能耗基线与验证设计.md`。

内容要求：

- 确认首个可实现的能耗基线、输入字段、适用范围和不足。
- 说明功率 × 时间得到能量时的单位、积分/聚合方式及辅助负载边界。
- 明确能耗预测与大语言模型无关，数值模型拟合不等于大模型微调。
- 给出固定航速基线与优化方案的公平对比方法：相同任务、参数和硬约束。
- 数据划分按航次/时间等相关分组设计，避免把相邻样本随机拆分造成泄漏。
- 指标包括预测误差、约束通过率、任务可行性、能耗和耗时；未实验的指标不填数值。
- 若采用网格搜索，只称离散候选范围内的搜索结果，不宣称连续全局最优。
- 指出 D2 首先实现哪些计算，哪些字段缺失会阻塞。

验收：A 能据此安排接口；C 能据此定义演示输入；B 次日无需重新决定基本计算口径。

| 缺少参数 | 缺初始 SOC、起终点或必要时间条件 | 明确追问，不生成完整数值方案 |
| 子航线/返程 | 选取中间港闸或反向路线 | 正确顺序、距离与适用约束 |
| 服务或工具失败 | 模型不可用或工具报错 | 明确失败/回退状态，不输出虚假成功 |

每条用例写：编号、输入、参数来源、预期状态、应显示字段、不能出现的行为、审核人。第一天的预期是测试设计，不是已通过测试。

不要默认约 189.8 km 全航线必然单次电量可达；正常演示路线须经 B 的能量预算确认。

界面草图仅需 Markdown/简单草图，包含任务输入、缺参提示、结果表、SOC/能耗展示、不可行原因、用户调整选项和假设提示。当天不要求漂亮 UI 或完整页面代码。

### C3. 需求素材、PPT 改动与佐证清单（P1）

交付：

- `docs/参赛/场景需求与素材索引.md`。
- `docs/展示/PPT最小修改清单.md`。
- `docs/参赛/佐证缺口清单.md`。

要求：

- 从已有资料整理真实用户、决策痛点、使用流程与场景边界，标注来源。
- 为需求分析章节提供文字要点，不虚构访谈、用户验证或部署记录。
- PPT 仅做必要调整：当前系统架构、实现范围、实际演示结果、团队信息与规则合规；不把全套重设计作为重点。
- 列出需要替换的页/元素、负责人和依赖成果；大 PPT 保留在共享资料中，不整份反复提交 Git。
- 佐证标明“已持有/待索取/无法提供”；专利、合作、测试证明必须有真实文件。
- 视频先确定 3–5 分钟展示主线，真实录制等待功能稳定。

验收：A 能直接用素材索引组织提纲；PPT 改动范围明确；佐证缺口有负责人。

## 七、代码与文档协作规则

### 1. 文件归属

| 文件范围 | 主编辑人 | 复核人 |
|---|---|---|
| schemas、公共依赖、core、README、接口契约 | A | B/C 按依赖复核 |
| 船舶配置、安全限制、数据检查、计算设计 | B | A；涉及航线由 C 参与 |
| 航线配置、别名、场景、界面与展示计划 | C | A；涉及数值由 B 参与 |
| 方案说明书提纲与统稿 | A | B/C 提供分章节素材 |

同一文档需要多人贡献时，先提交各自负责的独立素材文件，由主编辑人合并。Word/PPT 可在仓库保存版本，但不能像源码一样可靠地自动合并；避免同时改同一个二进制文件。

### 2. 第一天建议分支

- A：`feature/d1-contracts`。
- B：`feature/d1-vessel-data`。
- C：`feature/d1-route-cases`。

从最新 main 创建各自分支。后续具体模块另开分支。B/C 不直接改公共接口；确需改动先向 A 提出。

示例流程（在自己的仓库目录执行）：

```powershell
git switch main
git pull --ff-only
git switch -c feature/d1-vessel-data
git status
# 完成自己负责的文件后，只暂存本次实际修改的文件
git add configs/vessel_facts.yaml docs/数据/船舶参数与冲突清单.md
git commit -m "Document vessel facts and parameter conflicts"
git push -u origin feature/d1-vessel-data
```

然后在 GitHub 创建 PR，写明交付路径、测试结果、接口影响、已知缺口。上例只演示流程，不代表所有 B 的文件都已提交。若 pull 失败或有未提交修改，不执行强制覆盖，先报告 A。

### 3. PR 与安全检查

- 每个 PR 尽量对应一个清晰任务，避免把不相关文件混在一起。
- A 审查 B/C；A 的公共接口由 B/C 交叉审查。
- 合并前确认路径、单位、来源、空值语义和测试结果。
- 不提交真实密钥、虚拟环境、原始大数据、完整大型 PPT、缓存和敏感坐标。
- 检查 `git diff --check`，合并后跑基础测试。
- GitHub 是共享源文件和审查入口；大素材继续通过资料包/网盘协作。
