# 反思循环与意图翻译器设计计划

> 本文档定义"不可行 → 反思 → 妥协选项 → 船员拍板 → 意图翻译 → 重算"的完整机制。
> 配套:`Agent图结构计划.md`(完整设计参考)、`本周实现范围与接口要求.md`与七日任务表(本周执行)。
> 状态:靶子稿,待进一步探讨。

## 0. 定位与目标

解决图结构计划里一个未显式设计的漏洞:**反思循环里,LLM/船员提的"意图"到底怎么变成"让工具重新计算并得到不同结果"的输入修改?**

核心结论(一句话):

> 反思能让结果改变,靠的不是"再调一次工具",而是**"意图翻译器"把意图翻译成优化问题的输入修改(插补能点/改约束/改出发时间),工具在变化后的输入上重新求解**。数值始终由工具算,不经过 LLM 或船员。

## 1. 反思循环完整机制(含 HITL)

关键设计(用户拍板):**约束软硬不在设计期定死,而是不可行时枚举妥协选项、问船员选哪种。** 这是 human-in-the-loop。

```
Tspeed 算出不可行 + violation_reason
        │
        ▼
intent_translator 枚举"妥协选项"      ← 对每个可调方向试算一次,得到带数值的选项
  例:[ ①晚到15分钟  ②到港SOC降到20%  ③提前30分钟出发
       ④在漯河港补35分钟  ⑤全程降速到8.1节  ⑥放弃 ]
        │
        ▼
interrupt(暂停) —— 把选项抛给船员:"你能接受哪种妥协?"
        │
        ▼
船员选择(或答"都不能接受" → give_up)
        │
        ▼
intent_translator 把选择 → 输入修改
        │
        ▼
工具用修改后的输入重新求解 → 可行?
        ├─ 可行 → 继续 tmanagement → report
        └─ 仍不可行 → 回 interrupt 再问(最多2轮)
```

**演示模式**:用户本人就是船员,由用户真实选择妥协方向(不做自动模式/预设选择)。

## 2. 不可行场景枚举

| # | 不可行场景 | violation_reason 示例 | 可能的妥协方向 |
|---|---|---|---|
| 1 | 时间不可行 | "限速内最快航速仍无法 18:00 前到港" | 放宽时间 / 提前出发 / 放弃 |
| 2 | SOC 不可行 | "满足时间则到港 SOC 18% < 25% 报警线" | 降速 / 补能 / 放宽 SOC / 放弃 |
| 3 | 限速/管制冲突 | "X 段限速 6 节导致该段耗时过长" | 放宽时间 / 提前出发 |
| 4 | 补能点不足 | "航程过长,中途补能点覆盖不了电量需求" | 放弃 / (换航线,暂不支持) |
| 5 | 功率/温升风险 | "X 段需功率 200kW > 额定 140kW" | 降速(降功率) |
| 6 | 船闸时间窗冲突 | "到 X 闸时间落在放行窗口外,需等 2 小时" | 调整出发 / 微调航速 |
| 7 | 吃水/水深约束 | "满载吃水 3.2m > X 段水深 2.8m" | (需减载/换航线,暂不支持) |
| 8 | 电池 SOH 不足 | "实际可用容量 < 标称,电量撑不到" | 补能 / 降速 / 放弃 |

**MVP 建议先做 1~6**,7、8 作为场景预留(它们涉及减载/换航线,超出"航速+能量"主任务)。

## 3. 意图动作空间(妥协选项类型)

在 HITL 下,"意图"本质是**船员可选的妥协方向**。方向由工具枚举(每个方向带工具试算好的具体数值),船员只选方向、不选数值。

| 意图(妥协方向) | 选项呈现(数值由工具算) | 本质 |
|---|---|---|
| `accept_late` | "晚到 15 分钟" | 放宽到港时间约束 |
| `accept_lower_soc` | "到港 SOC 降到 20%(高于断电线)" | 放宽 SOC 下限 |
| `adjust_departure` | "提前 30 分钟出发" | 平移时间轴 |
| `recharge` | "在漯河港补 35 分钟" | 插入补能断点 |
| `slow_down` | "全程降到 8.1 节" | 时间约束软化为"省电优先" |
| `give_up` | "放弃,接受不可行" | 终止,输出不可行报告 |

**关键原则:选项里的数值(15分钟、20%、35分钟、8.1节)全是工具试算出来的,船员/LLM 只选"方向",永不编数值。**

## 4. 意图翻译器设计(独立组件,用户已拍板)

### 4.1 定位

- **独立确定性组件**(规则/搜索),不是 LLM,不是工具的一部分。
- 职责:**枚举妥协选项 + 把选择翻译成输入修改**。
- 放在 `reflection` 之后、工具重算之前(图结构计划里 `reflection → tseg` 这条边需要拆成 `reflection → intent_translator → 工具`)。

### 4.2 输入输出

```
输入:intent(船员选的方向) + current_state(不可行状态 + 原约束 + 原航段)
输出:modified_inputs(修改后的优化问题输入)
```

### 4.3 核心映射表(意图 → 输入修改 → 重算的工具)

| 意图 | 翻译动作(确定性) | 修改哪个输入 | 重算走哪个工具 |
|---|---|---|---|
| `accept_late` | 到港时间 T → T+Δ | `constraints.time_limit` | Tspeed |
| `accept_lower_soc` | SOC 下限 25% → 20% | `constraints.soc_min` | Tspeed |
| `adjust_departure` | 出发时间 ±Δ | `voyage_request.departure_time` | 整链重算(Tseg 起) |
| `recharge` | 在选定补能点插入补能断点 | `segments`(插点) | Tseg → Tenergy → Tspeed |
| `slow_down` | 时间约束硬 → 软(加惩罚项) | `constraints`(时间软硬) | Tspeed |
| `give_up` | 不改,终止 | — | 输出不可行报告 |

### 4.4 "枚举选项"怎么得到数值

枚举阶段,`intent_translator` 对每个可调方向**试算一次**(调对应工具),得到该方向的可行解数值,拼成选项列表。这本质是**对优化问题做敏感性探测**:

- "晚到多少分钟能行?" → 试算 → 15 分钟
- "降到几节能行?" → 试算 → 8.1 节
- "在哪个点补多久?" → 枚举补能点试算 → 漯河港 35 分钟

### 4.5 相关性机制:不可行类型 → 候选意图(回答"相关性怎么得到")

"只枚举相关 2~3 个"的相关性,来自一张**规则化的映射表**,不是 LLM 临时判断:

1. 工具输出不可行时,除了自然语言 reason,还必须输出**结构化的 `infeasible_type` 枚举**;
2. `intent_translator` 查表,得到"该类型的候选妥协方向"。

| infeasible_type | 候选意图 |
|---|---|
| `time_infeasible` | accept_late、adjust_departure、give_up |
| `soc_infeasible` | slow_down、recharge、accept_lower_soc、give_up |
| `speed_limit_conflict` | accept_late、adjust_departure、give_up |
| `charging_insufficient` | recharge、give_up |
| `power_risk` | slow_down、give_up |
| `lock_timewindow` | adjust_departure、slow_down、give_up |

这张表就是"领域知识"的规则化(资深航海专家知道"SOC 不够 → 降速/补能/放宽"),由设计者编码,运行时 LLM 不参与判断相关性,只负责把选项文案化。

### 4.6 多轮反思:同方向增量搜索(回答 7.2)

第一轮船员选了方向但试算仍不可行,第二轮**不换方向,而是在同一方向上加大幅度继续找**:

> 第一轮:船员选"晚 15 分钟" → 试算 → 仍不可行
> 第二轮:intent_translator 沿 accept_late 方向增量搜索(20/25/30/40 分钟)→ 找到"晚 40 分钟可行" → 把新方案再给船员确认

本质是**船员定方向,工具沿方向找"最小可行妥协量"**。最多 2 轮。

### 4.7 recharge 的补能点推荐(回答 7.4)

多个补能点都可行时,工具枚举所有可行点,**附上推荐项 + 推荐原因**:

- 推荐原因要业务化:更符合航段划分 / 更符合电池健康 / 更符合"饭点"(船员可趁补能吃饭休息)。

`intent_translator` 给每个可行点算一个"推荐分"(综合考虑航段契合度、电池健康、停靠时段),LLM 把推荐理由用船员能懂的话讲出来。

## 5. 工具能力评估与匹配

### 5.1 当前 5 工具够不够

| 工具 | 现状 | 反思循环需要什么 | 结论 |
|---|---|---|---|
| Tdata | ✓ | — | 够 |
| Tseg | ✓(补能迭代已设计) | 支持插入/移除补能点 | **够,复用 §5 补能迭代** |
| Tenergy | ✓ | — | 够 |
| Tspeed | ✗ 约束写死 | **约束可调**:时间硬/软、SOC 下限可改、出发时间可改 | **最大缺口,需扩展** |
| Tmanagement | ✓ | — | 够 |

### 5.2 需要新增/扩展(用户已拍板"允许按需新增")

1. **扩展 Tspeed**:把"约束"从写死参数改成可传入、可修改的对象(时间软硬、SOC 下限、出发时间)。这是支撑 accept_late / accept_lower_soc / adjust_departure / slow_down 的前提。
2. **新增 `intent_translator` 组件**(§4):枚举选项 + 翻译。可放 `core/` 下,不一定是独立"工具",但必须是独立可测的组件。
3. **可选新增"补能规划"逻辑**:recharge/change_recharge_point 的"枚举补能点 × 补能时长"搜索。可复用 Tseg 补能迭代,若复杂度上升再独立。

### 5.3 质量判断

- 数量:5 工具基本够,核心是"扩展 Tspeed 的约束可调" + "新增 intent_translator",不必硬凑新工具。
- 质量:当前工具是"一次性求解器",缺的是"接受可变约束/可变输入"的能力。补齐 Tspeed 约束可调后,其余意图都能落地。

## 6. 与图结构计划的对接

图结构计划里,反思循环这段要改成:

```
tspeed → feasible=False
        │
        ▼
reflection(intent_translator 枚举选项)
        │
        ▼
interrupt(问船员)  ← 新增 HITL
        │
        ▼
intent_translator(选择 → 输入修改)
        │
        ▼
Tseg/Tspeed 重算(修改后的输入)
```

即:`reflection → tseg` 这条边,拆成 `reflection → intent_translator → interrupt → intent_translator → 工具`。

## 7. 已定决策(本轮拍板)

1. **枚举粒度**:按 `infeasible_type` 只枚举相关 2~3 个方向(见 §4.5 映射表)。
2. **多轮反思**:第一轮不行,第二轮沿船员所选方向增量搜索,找到可行解再问船员(见 §4.6);最多 2 轮。
3. **演示模式**:演示时用户本人就是船员,由用户真实选择,不做自动模式/预设选择。
4. **补能点选择**:多个可行点全部枚举,附推荐项 + 业务化推荐原因(见 §4.7)。
5. **试算方式**:枚举选项时调用真工具推演,不内嵌简化搜索。

## 8. 一句话总结

> 反思循环 = **不可行 → 工具枚举妥协选项 → 问船员拍板 → 意图翻译器把选择变成输入修改 → 工具重算**。意图翻译器是独立确定性组件,核心是那张"意图 → 输入修改 → 工具"映射表;最大的工具缺口是 **Tspeed 的"约束可调"接口**。
