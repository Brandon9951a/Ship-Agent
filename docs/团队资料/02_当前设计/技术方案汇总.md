# 绿航智算智能体 —— 项目说明书

> 大语言模型驱动的船舶航速优化与能量管理智能体
> 本文档记录完整技术设计目标，不是已实现功能清单。本周范围以《本周实现范围与接口要求.md》及《../00_必读/七日任务与参赛交付表.md》为准，结果以实际代码与测试为准。
> 配套设计文档：`Agent图结构计划.md`（图结构参考）、`反思循环与意图翻译器设计计划.md`（反思机制）。

## 1. 项目概述

### 1.1 项目定位

本项目构建一个 **"数值可信的航行智能体"**，面向 **豫交投 001 纯电动内河船**，服务于 **平顶山港 — 周口港** 航线（全程 8 段约 189.8 km，途经 6 座船闸）。

智能体以自然语言（模拟船员口语，后续接入语音）为入口，自动完成：

```
任务理解 → 数据获取 → 航段划分 → 能耗预测 → 航速优化 → 能量管理 → 可解释输出
```

### 1.2 一句话目标

> **LLM 负责语义决策，确定性工具负责数值计算，数值锁定与反思循环保证结果可靠。**

### 1.3 核心挑战与应对

| 挑战 | 应对 |
|---|---|
| 大模型容易"编数值"（航速 / 能耗 / SOC / ETA） | **数值锁定**：数值全部由确定性工具产出，LLM 只解释不产数 |
| 不可行任务（时间不够 / 电量不够）无法硬解 | **反思循环**：工具枚举妥协选项，船员拍板，重算 |
| 航中环境会变化，方案需要动态调整 | **航中滚动重规划** + 自建环境仿真器 |
| 决策权边界模糊，模型可能越权 | **决策权边界**：LLM 只自主 parse / reflection / report 三处，其余规则锁死 |

## 2. 总体技术路线

### 2.1 两条核心设计原则

1. **语义给 LLM，计算给工具，边界用规则兜底。**
2. **让 LLM 做"选择题"，不让 LLM 做"填空题"** —— LLM 决策的选项和后果都由工具产出，LLM 只行使"选哪个 / 怎么解释"的决策权。

### 2.2 总体架构：三层 + LangGraph 底座

```
┌──────────────── 决策层（LLM）────────────────┐
│   语义理解 / 妥协权衡 / 解释说服               │
└────────────────┬─────────────────────────────┘
                 │ 结构化意图 / 约束
┌────────────────▼────────────── 计算层（工具）─┐
│   数据获取 / 航段划分 / 能耗预测 /            │
│   航速优化 / 能量管理                        │
└────────────────┬─────────────────────────────┘
                 │ 权威数值
┌────────────────▼────────────── 安全层（规则）─┐
│   数值锁定 / 可行性校验（规则兜底）           │
└──────────────────────────────────────────────┘
```

- **决策层**：LLM 只做三件事——语义解析、妥协选项呈现、报告解释，不产任何工程数值。
- **计算层**：五个确定性工具完成全部数值计算，输入输出均为结构化类型（dataclass / JSON），杜绝自由文本传值。
- **安全层**：数值锁定与可行性校验，用规则兜底，保证结果可信、可追溯。

**框架选型**：LangGraph 作底座（状态机 + 节点 + 条件边 + checkpoint + HITL）。创新点落在"领域逻辑 + 数值可信性"，不在框架本身。

### 2.3 技术栈

| 层 | 技术 |
|---|---|
| 编排框架 | LangGraph（状态机 + 节点 + 条件边 + checkpoint + `interrupt` HITL） |
| 决策层模型 | 云端模型API（实际提供方与model由D1试通后定版，配置化） |
| 计算层 | 纯 Python 确定性工具（dataclass 结构化输入输出） |
| 领域模型 | 物理三次方/残差学习能耗模型、DE/网格航速优化、FDP 能量管理 |
| 环境 | 自建轻量船舶-航道环境仿真器（软件在环 SIL） |
| 界面 | Gradio 文本版（一期），语音入口（二期） |

## 3. Agent Loop 图结构设计

整个智能体用 LangGraph 编排成一张图。节点分五类，由 7 条条件边路由。

### 3.1 State 状态定义

LangGraph 的共享状态，贯穿全图，是所有节点读写的统一契约：

```python
class AgentState(TypedDict):
    # 对话历史（LLM 上下文，add_messages 追加）
    messages: Annotated[list, add_messages]

    # 任务与解析
    voyage_request: dict        # VoyageRequest —— parse 输出
    need_clarify: bool          # 是否缺关键字段，需追问
    clarify_question: str       # 追问内容

    # 数据
    vessel_state: dict          # VesselState —— tdata 输出

    # 航段与能耗
    segments: list              # list[RouteSegment] —— tseg 输出
    energy_results: list        # list[EnergyCandidate] —— tenergy 输出
    optimization: dict          # OptimizationResult（含 feasible）—— tspeed 输出
    management_plan: dict       # ManagementPlan —— tmanagement 输出
    voyage_plan: dict           # VoyagePlan —— 汇总

    # 反思 / 重规划
    feasible: bool              # 可行性标志
    violation_reason: str       # 不可行原因
    replan_count: int           # 反思 / 重规划轮次
    in_transit_state: dict      # 航行进行状态（当前位置 / 实际SOC / 已走里程），航中重规划用

    # 校验与输出
    value_lock_pass: bool       # 数值锁定是否通过
    report: str                 # 最终报告
    trace: list                 # AgentTrace（ReAct 风格，Observation 由工具填充）
```

### 3.2 节点清单（五类）

#### 3.2.1 LLM 决策节点（3 个，真 Agent 的"决策权"所在）

| 节点 | 决策内容 | 方式 |
|---|---|---|
| `parse_node` | 船员口语 → `VoyageRequest` | 语义抽取，落在 schema；关键字段（起终点 / SOC / 时间）规则二次复核 |
| `reflection_node` | 把妥协选项文案化 + 解释推荐原因 + 和船员对话 | 呈现 / 解释；选项和数值由 intent_translator + 工具产出 |
| `report_node` | `VoyagePlan` → 船员语言 | 润色解释；数字必须来自 plan（数值锁定） |

#### 3.2.2 确定性工具节点（5 个，计算权，规则锁死）

| 节点 | 职责 | 决策权 |
|---|---|---|
| `tdata_node` | 补全船舶 / 电池 / 环境状态 | 锁死：用户输入优先 → 历史分布 / 默认 |
| `tseg_node` | 航段划分（8 类断点 + 激活条件） | 锁死：断点识别 / 激活规则化 |
| `tenergy_node` | 能耗预测（物理模型） | 锁死 |
| `tspeed_node` | 航速优化（DE / 网格），产出 `feasible` | 锁死 |
| `tmanagement_node` | 双电池能量管理（FDP） | 锁死 |

#### 3.2.3 确定性组件：意图翻译器

| 节点 | 职责 |
|---|---|
| `intent_translator` | 不可行时按 `infeasible_type` 枚举妥协选项；把船员选择翻译成优化问题的输入修改（详见 §4） |

#### 3.2.4 规则校验节点

| 节点 | 职责 |
|---|---|
| `value_lock_node` | 数值锁定：报告里的数字与 `VoyagePlan` 比对，偏离即拒绝并回退模板 |

#### 3.2.5 环境与追问节点

| 节点 | 职责 |
|---|---|
| `environment_node` | 读环境仿真器，输出当前环境；判断是否触发重规划（阈值 / 硬事件） |
| `clarify_node` | 缺关键字段时生成追问，交用户补充（用户输入 → 重新 parse） |

### 3.3 三条主链路

#### 链路一：航前基线规划（主流程）

```
START
  │
  ▼
parse_node(LLM)          口语 → VoyageRequest
  │
  ▼
{关键字段缺失?}          ← 规则（字段齐全性检查）
  ├─ 是 ──▶ clarify_node(追问) ──▶ END（等待用户补充）
  │
  └─ 否
       ▼
tdata_node(工具)         补全 VesselState
       │
       ▼
tseg_node(工具)          航段划分（含补能迭代，见链路三）
       │
       ▼
tenergy_node(工具)       能耗预测
       │
       ▼
tspeed_node(工具)        航速优化 → 产出 feasible + 到港SOC + ETA
       │
       ▼
{feasible?}              ← 规则（读 feasible bool，不交给 LLM 判断）
  ├─ 是 ──▶ tmanagement_node(工具) ──▶ report_node(LLM) ──▶ value_lock_node(规则) ──▶ END
  │
  └─ 否 ──▶ intent_translator(枚举妥协选项) ──▶ reflection_node(文案化) ──▶ interrupt(问船员)
                │
                ▼
            {船员选择?}
                ├─ 有方向 ──▶ intent_translator(翻译) ──▶ 回到 tseg_node（修改输入重算，最多 2 轮）
                └─ 放弃 ──▶ 输出"不可行报告 + 最接近的可行方案" ──▶ END
```

#### 链路二：航中滚动重规划

> 触发源 = 环境仿真器。环境变化是仿真器内生的，不是演示者假装。

```
（航行中，按已生成的方案推进）
  │
  ▼
environment_node(仿真器)  读当前环境 / 实际SOC / 临时限航通告
  │
  ▼
{偏差超阈值 or 硬事件?}   ← 规则（阈值比较 / 事件类型）
  ├─ 否 ──▶ 继续航行（不打断）
  │
  └─ 是 ──▶ ① 锁定已走完的航段
                │
                ▼
            ② 以"当前位置 + 当前真实状态"为新起点
                │
                ▼
            ③ 重跑 tseg → tenergy → tspeed → tmanagement（只重划剩余航程）
                │
                ▼
            ④ report_node（解释"方案为什么变" + 前后对比）──▶ value_lock_node ──▶ END
```

#### 链路三：补能迭代闭环（航段划分内部）

> 补能点是否停靠，依赖 SOC 规划；SOC 规划又依赖分段 → 迭代解耦。

```
tseg（初始分段：硬断点 + 任务断点 + 约束断点，【不含补能点】）
  │
  ▼
tenergy + tspeed  算全程 SOC 轨迹
  │
  ▼
{途中 SOC 跌破报警阈值（25%）?}   ← 规则
  ├─ 否 ──▶ 分段确定，继续主流程
  │
  └─ 是 ──▶ 在跌破点上游最近的补能点插入"补能断点"
                │
                ▼
            {迭代 < 3 轮?}   ← 规则
                ├─ 是 ──▶ 回到 tseg 重新分段
                └─ 否 ──▶ 判定不可行，转 reflection_node
```

**补能决策的 LLM 落点**：当存在多个候选补能方案时（如"在漯河港补 40 分钟" vs "全程降速 1 节省电不停靠"），工具枚举候选，`reflection_node` 做**选择题**并解释权衡。MVP 阶段先用纯规则（SOC 硬阈值 + 最近补能点），LLM 选择题作为亮点后加。

### 3.4 条件边路由（7 条）

| # | 条件边 | 谁决定 | 依据 |
|---|---|---|---|
| 1 | 关键字段缺失？（parse 后） | **规则** | 字段齐全性检查 |
| 2 | feasible？（tspeed 后） | **规则** | 求解器输出的 `feasible` bool |
| 3 | 补能 / 降速选哪个？（反思） | **船员拍板（HITL）** | 工具枚举选项，船员选 |
| 4 | replan_count 超限？（反思循环） | **规则** | 轮次计数（≤2） |
| 5 | 途中 SOC 跌破阈值？（补能迭代） | **规则** | SOC 轨迹 vs 25% 报警线 |
| 6 | 补能迭代超限？（补能迭代） | **规则** | 计数（≤3） |
| 7 | 环境变化触发重规划？（航中） | **规则** | 偏差阈值 / 硬事件 |

**核心原则**：凡"客观可判定"的分支（缺字段 / 可行 / 超限 / 阈值 / 触发）全部规则锁死；凡"有取舍权衡"的分支（补能还是降速）交给船员拍板。LLM 不参与路由判断——它的价值在"呈现选项、解释利弊"，不在"决定走哪条路"。

### 3.5 决策权边界总表（节点级）

| 节点 / 分支 | 类型 | 决策内容 | 锁死 / 自主 |
|---|---|---|---|
| parse | LLM | 口语 → 结构化约束 | 自主（关键字段规则复核） |
| 缺字段判断 | 规则 | 是否追问 | 锁死 |
| tdata | 工具 | 数据补全 | 锁死 |
| tseg | 工具 | 断点识别 + 激活 | 锁死 |
| 补能决策 | LLM（后加） | 停不停 / 在哪停 | 自主（规则兜底） |
| tenergy | 工具 | 能耗计算 | 锁死 |
| tspeed | 工具 | 航速求解 + 可行性 | 锁死 |
| feasible 分支 | 规则 | 可行 / 不可行 | 锁死（读 bool，不给 LLM） |
| reflection | LLM | 调整策略 | 自主（轮次规则兜底） |
| tmanagement | 工具 | 能量分配 | 锁死 |
| report | LLM | 生成解释 | 自主（数值锁定） |
| value_lock | 规则 | 数值校验 | 锁死 |
| environment | 规则 | 环境读取 + 重规划触发 | 锁死 |

**一句话**：LLM 自主的只有 3 处（parse / reflection / report），且每处都被"schema + 工具验证 + 规则兜底"三层约束；其余全是锁死的工具与规则。

### 3.6 LangGraph 概念落地对照

| LangGraph 概念 | 本项目落地 |
|---|---|
| State + reducer | §3.1 的 `AgentState` |
| Node（工具） | tdata / tseg / tenergy / tspeed / tmanagement |
| Node（LLM） | parse / reflection / report |
| Conditional edge | §3.4 的 7 条路由 |
| 循环边 | reflection → tseg（反思重规划）、补能迭代闭环 |
| Checkpointer | 支撑"可回溯"与 HITL |
| HITL（`interrupt`） | 反思循环问船员拍板；双电池切供能模式、不可行强制降速的人工确认 |
| 子图 | 环境仿真器作为独立子图 / 节点 |

## 4. 反思循环与意图翻译器

解决图结构中一个关键问题：**不可行时，船员提的"意图"怎么变成"让工具重新计算并得到不同结果"的输入修改？**

> **核心结论**：反思能让结果改变，靠的不是"再调一次工具"，而是**意图翻译器把意图翻译成优化问题的输入修改（插补能点 / 改约束 / 改出发时间），工具在变化后的输入上重新求解**。数值始终由工具算，不经过 LLM 或船员。

### 4.1 反思循环完整机制（含 HITL）

**关键设计**：约束软硬不在设计期定死，而是**不可行时枚举妥协选项、问船员选哪种**（human-in-the-loop）。

```
Tspeed 算出不可行 + violation_reason
        │
        ▼
intent_translator 枚举"妥协选项"      ← 对每个可调方向试算一次，得到带数值的选项
  例：[ ①晚到15分钟  ②到港SOC降到20%  ③提前30分钟出发
        ④在漯河港补35分钟  ⑤全程降速到8.1节  ⑥放弃 ]
        │
        ▼
interrupt（暂停）—— 把选项抛给船员："你能接受哪种妥协？"
        │
        ▼
船员选择（或答"都不能接受" → give_up）
        │
        ▼
intent_translator 把选择 → 输入修改
        │
        ▼
工具用修改后的输入重新求解 → 可行?
        ├─ 可行 → 继续 tmanagement → report
        └─ 仍不可行 → 回 interrupt 再问（最多 2 轮）
```

**演示模式**：用户本人就是船员，由用户真实选择妥协方向（不做自动模式 / 预设选择）。

### 4.2 不可行场景枚举（8 类）

| # | 不可行场景（`infeasible_type`） | `violation_reason` 示例 | 可能的妥协方向 |
|---|---|---|---|
| 1 | `time_infeasible` 时间不可行 | "限速内最快航速仍无法 18:00 前到港" | 放宽时间 / 提前出发 / 放弃 |
| 2 | `soc_infeasible` SOC 不可行 | "满足时间则到港 SOC 18% < 25% 报警线" | 降速 / 补能 / 放宽 SOC / 放弃 |
| 3 | `speed_limit_conflict` 限速/管制冲突 | "X 段限速 6 节导致该段耗时过长" | 放宽时间 / 提前出发 |
| 4 | `charging_insufficient` 补能点不足 | "航程过长，中途补能点覆盖不了电量需求" | 放弃 /（换航线，暂不支持） |
| 5 | `power_risk` 功率/温升风险 | "X 段需功率 200kW > 额定 140kW" | 降速（降功率） |
| 6 | `lock_timewindow` 船闸时间窗冲突 | "到 X 闸时间落在放行窗口外，需等 2 小时" | 调整出发 / 微调航速 |
| 7 | `draft_constraint` 吃水/水深约束 | "满载吃水 3.2m > X 段水深 2.8m" |（需减载/换航线，暂不支持） |
| 8 | `soh_insufficient` 电池 SOH 不足 | "实际可用容量 < 标称，电量撑不到" | 补能 / 降速 / 放弃 |

**MVP 建议先做 1~6**，7、8 作为场景预留（它们涉及减载 / 换航线，超出"航速 + 能量"主任务）。

### 4.3 意图动作空间（6 个妥协方向）

在 HITL 下，"意图"本质是**船员可选的妥协方向**。方向由工具枚举（每个方向带工具试算好的具体数值），船员只选方向、不选数值。

| 意图（妥协方向） | 选项呈现（数值由工具算） | 本质 |
|---|---|---|
| `accept_late` | "晚到 15 分钟" | 放宽到港时间约束 |
| `accept_lower_soc` | "到港 SOC 降到 20%（高于断电线）" | 放宽 SOC 下限 |
| `adjust_departure` | "提前 30 分钟出发" | 平移时间轴 |
| `recharge` | "在漯河港补 35 分钟" | 插入补能断点 |
| `slow_down` | "全程降到 8.1 节" | 时间约束软化为"省电优先" |
| `give_up` | "放弃，接受不可行" | 终止，输出不可行报告 |

**关键原则：选项里的数值（15 分钟、20%、35 分钟、8.1 节）全是工具试算出来的，船员 / LLM 只选"方向"，永不编数值。**

### 4.4 意图翻译器设计

#### 4.4.1 定位

- **独立确定性组件**（规则 / 搜索），不是 LLM，不是工具的一部分。
- 职责：**枚举妥协选项 + 把选择翻译成输入修改**。
- 放在 `reflection` 之后、工具重算之前（图结构里 `reflection → tseg` 这条边拆成 `reflection → intent_translator → interrupt → intent_translator → 工具`）。

#### 4.4.2 输入输出

```
输入：intent（船员选的方向） + current_state（不可行状态 + 原约束 + 原航段）
输出：modified_inputs（修改后的优化问题输入）
```

#### 4.4.3 映射表一：意图 → 输入修改 → 重算工具

| 意图 | 翻译动作（确定性） | 修改哪个输入 | 重算走哪个工具 |
|---|---|---|---|
| `accept_late` | 到港时间 T → T+Δ | `constraints.time_limit` | Tspeed |
| `accept_lower_soc` | SOC 下限 25% → 20% | `constraints.soc_min` | Tspeed |
| `adjust_departure` | 出发时间 ±Δ | `voyage_request.departure_time` | 整链重算（Tseg 起） |
| `recharge` | 在选定补能点插入补能断点 | `segments`（插点） | Tseg → Tenergy → Tspeed |
| `slow_down` | 时间约束硬 → 软（加惩罚项） | `constraints`（时间软硬） | Tspeed |
| `give_up` | 不改，终止 | — | 输出不可行报告 |

#### 4.4.4 映射表二：不可行类型 → 候选意图（相关性来源）

"只枚举相关 2~3 个"的相关性，来自一张**规则化的映射表**，不是 LLM 临时判断：

1. 工具输出不可行时，除了自然语言 reason，还必须输出**结构化的 `infeasible_type` 枚举**；
2. `intent_translator` 查表，得到"该类型的候选妥协方向"。

| `infeasible_type` | 候选意图 |
|---|---|
| `time_infeasible` | accept_late、adjust_departure、give_up |
| `soc_infeasible` | slow_down、recharge、accept_lower_soc、give_up |
| `speed_limit_conflict` | accept_late、adjust_departure、give_up |
| `charging_insufficient` | recharge、give_up |
| `power_risk` | slow_down、give_up |
| `lock_timewindow` | adjust_departure、slow_down、give_up |

这张表就是"领域知识"的规则化（资深航海专家知道"SOC 不够 → 降速 / 补能 / 放宽"），由设计者编码，运行时 LLM 不参与判断相关性，只负责把选项文案化。

#### 4.4.5 "枚举选项"怎么得到数值

枚举阶段，`intent_translator` 对每个可调方向**试算一次**（调对应工具），得到该方向的可行解数值，拼成选项列表。本质是**对优化问题做敏感性探测**：

- "晚到多少分钟能行？" → 试算 → 15 分钟
- "降到几节能行？" → 试算 → 8.1 节
- "在哪个点补多久？" → 枚举补能点试算 → 漯河港 35 分钟

#### 4.4.6 多轮反思：同方向增量搜索

第一轮船员选了方向但试算仍不可行，第二轮**不换方向，而是在同一方向上加大幅度继续找**：

> 第一轮：船员选"晚 15 分钟" → 试算 → 仍不可行
> 第二轮：intent_translator 沿 accept_late 方向增量搜索（20/25/30/40 分钟）→ 找到"晚 40 分钟可行" → 把新方案再给船员确认

本质是**船员定方向，工具沿方向找"最小可行妥协量"**。最多 2 轮。

#### 4.4.7 recharge 的补能点推荐

多个补能点都可行时，工具枚举所有可行点，**附上推荐项 + 推荐原因**：

- 推荐原因要业务化：更符合航段划分 / 更符合电池健康 / 更符合"饭点"（船员可趁补能吃饭休息）。

`intent_translator` 给每个可行点算一个"推荐分"（综合考虑航段契合度、电池健康、停靠时段），LLM 把推荐理由用船员能懂的话讲出来。

### 4.5 工具能力评估与缺口

| 工具 | 现状 | 反思循环需要什么 | 结论 |
|---|---|---|---|
| Tdata | ✓ | — | 够 |
| Tseg | ✓（补能迭代已设计） | 支持插入 / 移除补能点 | 够，复用补能迭代 |
| Tenergy | ✓ | — | 够 |
| Tspeed | ✗ 约束写死 | **约束可调**：时间硬/软、SOC 下限可改、出发时间可改 | **最大缺口，需扩展** |
| Tmanagement | ✓ | — | 够 |

**需要新增 / 扩展**：

1. **扩展 Tspeed**：把"约束"从写死参数改成可传入、可修改的对象（时间软硬、SOC 下限、出发时间）。这是支撑 accept_late / accept_lower_soc / adjust_departure / slow_down 的前提。
2. **新增 `intent_translator` 组件**：枚举选项 + 翻译，独立可测组件。
3. **可选新增"补能规划"逻辑**：recharge 的"枚举补能点 × 补能时长"搜索，可复用 Tseg 补能迭代。

## 5. 六项核心技术机制

### 5.1 数值锁定 —— 保证数值一致

LLM 报告里的每个数字，都和工具产出的 `VoyagePlan` 逐一比对；有偏离就带纠错提示重试 1 次，再偏离则回退模板报告。数值全程由工具产出。

**落点**：独立节点 `value_lock_node`，放在 `report_node` 之后、END 之前。

**策略**：纠错重试 + 回退模板兜底（组合）。

```
report_node（LLM 生成报告）
      │
      ▼
value_lock_node（校验数字）
      │
      ├─ 通过 ──► 直接用（保留自然表达）
      │
      └─ 不通过 ──► 带纠错提示重试 1 次（"耗电 780 与工具 812 不符，请改"）
                     │
                     ├─ 改对 ──► 直接用
                     └─ 还错 ──► 回退模板报告（底线，必对）
```

**实现要点**：

- `value_lock_node` 抽取报告数字 → 与 `VoyagePlan` 字段逐一比对。
- 不通过 → 带纠错提示回到 `report_node`（重试 1 次）→ 再校验。
- 重试后仍不通过 → 用模板重新渲染（只引用 plan 字段，数字必然正确），`value_lock_pass=False`。
- 独立节点：职责单一、可单测、显式出现在 trace 里。

### 5.2 反思循环（HITL）—— 不可行场景的处理

方案不可行时，流程是：**工具枚举妥协选项（带算好的数值）→ 船员确认 → 意图翻译 → 重算**。船员选方向，工具算数值。（完整机制见 §4）

### 5.3 意图翻译器 —— 反思的引擎

把船员的妥协方向（降速 / 补能 / 放宽时间…）翻译成"优化问题输入修改"，让工具在变化后的输入上重新求解。（完整机制见 §4）

### 5.4 环境仿真器 —— 航中环境数据来源

自建轻量"船舶 + 航道"仿真器（软件在环 SIL），提供会变化的航中环境（风 / 流 / 水深 / 限航），支撑航中重规划。

**定位（关键）**：仿真器只负责"提供会变化的环境数据"（感知源），不负责算航速 / 能耗 / 能量分配（那仍是 Tenergy / Tspeed / Tmanagement 的职责）。**仿真器 = 环境，不是求解器。**

**模块构成**：

| 模块 | 内容 |
|---|---|
| 纵向动力学模型（1-DOF） | 速度 ↔ 阻力 ↔ 功率 ↔ 电耗 |
| 航道环境场 | 沿里程的风速 / 流速 / 水深 / 闸口 / 港口 / 限速区分布（静态场 + 时变演化） |
| 扰动事件 | 临时限航、风突变、SOC 实际值偏离等，可注入触发重规划 |
| 典型场景 | 预设（平流默认 / 逆风 6 级 / 能见度低 / 高水位） |

**决策权边界**：环境数据由仿真器 / 规则产出，LLM 不编环境数值。

### 5.5 约束驱动的航段划分

按"航速决策约束是否突变"分段——断点 = 会让航速决策约束突变的地方，而不是"有闸口 / 港口就切"。采用**候选断点 + 激活条件**模型，只有激活的断点才真正切段。

**8 类断点**：

| 断点类型 | 激活条件 |
|---|---|
| 船闸 | 硬断点，必切（过闸减速 / 等待 / 排队，闸前后独立） |
| 港口 / 码头 | 条件切——本航次有停靠 / 装卸 / 上下客任务才切，路过不停靠不切 |
| 补能点 | 条件切——SOC 规划需要补能才切（迭代确定） |
| 限速区 / 桥区 / 管制区 | 必切（航速上限突变） |
| 水深 / 吃水受限区 | 条件切（水深逼近吃水才切） |
| 气象突变点 | 阈值触发（风 / 能见度引发限速才切） |
| 水文突变点 | 阈值触发（流速方向 / 大小突变才切，平流不切） |
| 时间锚点 | 任务切（"18:00 前过某闸"这类硬时间约束） |

**气象 / 水文处理**：航前不作为断点（拿不到准确未来环境），只作段内参数（预报 / 历史常态 / 典型场景填充）；航中真实变化才触发重分段。

### 5.6 航中滚动重规划 —— 动态调整能力

环境变化时，以当前位置为新起点，只重划未走完的剩余航程。（完整流程见 §3.3 链路二）

## 9. 设计原则与验收标准

### 9.1 设计原则

- **数值与计算分离**：数值由确定性工具产出，LLM 只负责语义决策，保证数值可信与可验证。
- **可行性客观判定**：可行性由求解器结果判定，保证判断的客观性与一致性。
- **关键决策人工确认**：不可行时的妥协方向由船员确认，符合航运决策流程与合规要求。
- **自建仿真器**：可控、可解释、易与 Agent 集成。

### 9.2 全局约束

1. **结构化优先**：工具输入输出一律 dataclass / JSON，禁止靠自由文本 + 正则传数值。
2. **数值锁定**：LLM 只做解释润色，不产生航速 / 能耗 / SOC / ETA / 功率等工程数值。
3. **不可行必须拒绝**：不可行任务返回原因 + 调整建议，禁止编造假方案。
4. **数值可追溯**：报告里每个数字都能追溯到工具字段；船舶参数以 `vessel_facts.yaml` 为唯一事实源。
5. **Observation 由工具生成**：ReAct Trace 的 Observation 必须来自工具结果，不由模型编造。

### 9.3 验收标准

- 所有推荐航速、能耗、ETA、SOC、功率分配都来自工具结构化结果。
- 工具链顺序符合说明书：`Tdata → Tseg → Tenergy → Tspeed → Tmanagement`。
- 不可行任务必须说明原因和调整建议，不得强行输出方案。
- 输出同时包含分段表格和自然语言解释。
- ReAct Trace 可展示每一步 Thought / Action / Observation，但 Observation 必须由工具生成。
- 第一阶段文本 Demo 可稳定跑通；语音和重训不阻塞 MVP。
- 不可行时能走完"枚举选项 → 船员选择 → 重算"闭环。
